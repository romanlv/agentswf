usage: awf reply <run> <agent> [--to <id>] [--as <participant>] [<text>]
       awf send <run> <agent> [--as <participant>] [<text>]
       awf send <run> --as <participant> --event-id <id> [--author <name>] [<text>]
each takes [--cwd <directory>] [--run-root <directory>] [--json]

A run is <workflow>/<id>, or an <id> only one workflow has, here or in a project awf knows.
Answers a question an agent asked a participant outside the run, or messages an agent first,
over a route the workflow allowed. The text is the argument, or stdin without one. --to names
the question, as awf inbox prints it; it may be left out when the agent has one open. --as
names the participant when the workflow connects more than one. Neither waits for an answer:
it comes back in awf inbox. send --event-id is deprecated: awf emit <run> <participant>:reply
'{"text":…,"author":…}' --event-id <id> replaces it, and it forwards there. It still sends a
message on a participant to the run's code, the id the message's own, and prints as awf emit
does; it exits 0 for whatever the run did with it (accepted, duplicate, or refused by a run that
returned); 1 when the run or participant isn't found, or its attempt didn't start.

With --json, each prints {"v": 3, "id": …} when delivered, or a refusal whose code says why: the
participant's, or usage, no-run, ambiguous, id, unreachable, no-engine, other-engine or
internal-error. Exits 0 when delivered, 1 when refused (the code says why), 2 on a usage error,
3 when the run could not be reached.
